## 1. Design

### 1.1 One command, three kinds of section

| Section | What it is | Drives the exit code? |
|---|---|---|
| `1`–`12` | The SPEC §4 acceptance criteria. Each is a criterion of record. | yes — a failure here is a criterion that stopped holding |
| `P`, `X`, `G`, `F` | Not §4 criteria: the plan-validation hole, the §3.4 polymorphic table, a golden re-check, and a frozen-input verification. | yes, via the blocker tally, and deliberately kept out of the 12-criteria count so debt is never mistaken for a criterion failure |

The summary prints them separately for that reason:

```
  criteria demonstrated with both a firing and a passing case: 12 of 12
  assertions: 186 ok, 0 failed, 5 not demonstrable here
✗ 3 KNOWN BLOCKER(S) — surfaced, not swallowed:
```

### 1.2 Every criterion in both directions

A check that has only ever been seen to pass has not been seen to work. So each criterion asserts a
**firing** case (a known-bad input that must be rejected, with the *message* checked, not just the exit
code) and a **passing** case (a known-good input that must be accepted). Where the two differ by one
field, the harness says so out loud — e.g. criterion #12's two diversity fixtures are *identical* in
domains and source types, so the only thing the new rule can be reacting to is the shape.

Four assertion helpers, all of which read the *real* exit code:

- `exits <rc> <label>` — the exit code, printed in the label so it is in the evidence.
- `has <regex> <label>` / `hasnt <regex> <label>` — the message says the right thing. `hasnt` matters as
  much as `has`: it is how "the key_art clause is INERT on #18" and "`--strict` must not promote the
  off-list-token warning" are asserted.
- `truth <0|1> <label> <detail>` — a computed fact (a count, a digest, a file's absence).

`run()` is the only thing that executes anything, and it stores `$?` immediately. Nothing in this
harness pipes a command whose status matters, redirects a stderr to `/dev/null`, or writes `|| true`
after something that can fail. That is not fastidiousness — it is the exact bug this WP was sent to fix,
one file over.

### 1.3 Firing cases come from git where they can

Three criteria assert against the code *as it was*, materialised out of git into a temp dir:

| Criterion | Baseline | Why |
|---|---|---|
| 10 | `394b2af:scripts/mirror-images.py` | the pre-WP-8 script has no manifest concept at all — 0 occurrences of the word |
| 11 | `git archive 394b2af functions/daily` | the pre-WP-7/WP-11 daily, whole tree (score.js imports db.js, so a single-file checkout will not load) |

A firing case against the real prior code proves the criterion describes a change. A synthetic one only
proves the check can be made to fire.

### 1.4 Fixtures: generated where they are big, literal where they are small

WP-4's 32-case matrix and WP-5's plans/bundles/states both lived in the scratchpad and both WPs flagged
that WP-10 should own permanent copies. Both are now here, merged into a **single generator** plus a
handful of small literal files:

```
references/fixtures/coverage-rebuild/
  README.md                          how to run it, what each fixture is, how to add one
  build-fixtures.py                  → weekly/ 29 html · states/ 8 · plans/ 8 · bundles/ 3
  check-daily-routing.mjs            criterion #11's driver (lives here per the §2 ownership map)
  html/  diversity-{one-shape,three-shapes,bad-enum,all-key-art}.html   (#12, ~1 KB each)
         cover-{nd,permissive,unknown-licence}.html                     (#9,  ~0.5 KB each)
  json/  cover-licences.json                                            (#9)
  rss/   bbc-{cricket,cycling,athletics}-sample.xml                     (#11)
```

**Why the 29 rendered-issue fixtures are generated and not committed.** Each is frozen Issue #18
(141 KB) with exactly one thing changed. Committing the outputs means ~4.5 MB of near-identical HTML in
which the one line that matters is invisible — *a fixture nobody can read is a fixture nobody will
maintain*. Committing the mutations makes the whole matrix readable, one screen per criterion, and it
fails loudly rather than silently if an anchor ever moves: `one()` asserts the anchor exists before
replacing it, so a wrong `--issue` is a `SystemExit`, not a fixture that quietly wasn't mutated and then
passed every check.

The trade is named rather than hidden: a generated fixture depends on its input. That is acceptable
*only* because the input is frozen by SPEC §1.3 — and the harness checks it (§ 3) instead of trusting
it.

The state fixtures come in two deliberately different shapes. `states/weekly-*.json` are **full** copies
of the real state with one key replaced, because `validate-issue.py` reads five state keys at once and a
partial state would exercise its tolerance paths instead of the rule under test.
`states/rutted-*.json` and `states/open-loop-matured.json` are **minimal** standalone objects, because
the two upstream validators read one key each and a ten-line ledger is readable.

### 1.5 Invented data is labelled as invented

Two fixtures need a calendar event or a loop the real seed cannot supply. Every such row is prefixed
**`FIXTURE DATA — not a real event`**, so it can never be read as a fact of record if it is grepped out
of context. `rss/bbc-cycling-sample.xml`'s two titles carry `Fixture item, not a result` for a related
reason: unlike the cricket and athletics fixtures, whose titles are **live headlines quoted from
`EVIDENCE/WP-7.md` §3.3**, WP-7 recorded cycling's hit rate without quoting a single title, so there was
nothing to quote — those two lines are written to exercise the real keyword set and name no rider and no
outcome. No fixture asserts a 2026 result, venue or fixture date the repo does not already carry.
